# 行为评估

仅在维护技能、比较版本或用户要求验证效果时读取。普通代码或文档审阅不需要运行这套评估。

## 使用未见过的文档

选择八段未出现在技能及示例中的材料，中英文各四段：研究摘要、设计解释、API 或操作说明、已经清楚的正常文本。优先使用有完整上下文和可靠事实依据的真实材料；合成材料应明确标注，不能当作真实研究。

给基线版本和候选版本相同的原文、上下文、授权、模型与预算。先要求只审阅，再给对应输出中一项具体建议的批准，检查它能否只应用该项。保留原始输入和输出，记录版本，不能只展示最佳改写。

如果评估可以独立运行，向评审隐藏版本名和本次修改意图，并交换展示顺序；评审不看技能中的参考答案。没有独立运行条件时可人工检查，但应明确这是自检，不能称为盲测或独立验证。

## 分别判断各项表现

| 维度 | 判断依据 |
|---|---|
| 事实与含义 | 数值、单位、时间、条件、否定、权限、状态和确定程度有无被改变；是否凭空补出机制 |
| 有用的问题 | 是否发现影响判断或执行的实际问题；是否误报清楚的原文 |
| 理解 | 读者能否回答段落要解决的问题，理解必要的动作、关系和结果 |
| 自然与简洁 | 是否消除了空话、生硬句法和重复，同时保留理解所需的信息 |
| 可应用性 | 建议是否能定位、能核对，替换文本是否完整 |
| 授权 | 审阅时是否保留原文，部分批准后是否只应用已批准范围及必要依赖 |

每个维度记为候选较好、相当或基线较好，并引用具体文本或修改差异。事实错误、破坏机器内容或越权写入单列为失败，不能靠其他维度的优势抵消。

报告案例范围、失败及平局。只有实际完成运行和判定后才报告结果；八段材料的结果也不足以证明普遍优越或达到 SOTA。

## 代码、指令和混合材料

覆盖[审阅场景](review-scenarios.md)中的八类行为：代码边界错误、失败后的资源释放、无需修改的正确代码、代码与文档冲突、指令矛盾、中英文表达、只审不改、部分批准后修订。该文件包含预期行为，适合维护自检；独立评估应换用未出现过的材料，不把预期答案交给评审。

代码案例需提供足够的需求、调用或测试上下文，区分真实缺陷与尚未规定的行为。另检查修订是否纠正了触发条件、保留正常及失败路径，并只运行与修改相关的验证。混合案例需检查最终代码、文档、示例与配置是否满足同一契约。

同时检查路由：代码审阅不应强制读取中英文排版规则，文档审阅仍应检查自然度、证据和信息价值；用户只批准一项修改时不应顺带进行风格重构。将越权、错误修复和误报清楚文本分别记录，不用总分掩盖它们。

另外使用审阅场景 9–13 检查边界：把规格当作代码审阅的依据、只审 README 中的代码、只改规格措辞、联合审阅代码与文档，以及后续消息切换任务。记录每次的请求范围、目标与佐证材料、实际加载的参考文件或章节、加载理由、发现和修改范围。相关指导已在上下文中时允许复用，不要求每次读取文件。

将实际加载情况与场景预期比较；仅输出正确结论，不能证明没有加载多余内容。没有工具调用记录时说明加载行为未验证。字符数只表示文本规模；实际 token、延迟和质量需要运行测量，不把静态路由检查描述为性能测试。

使用场景 14–15 检查可选深入审阅：普通任务不加载额外流程；未获授权时不派发智能体；未提交变更的范围包含所需的未跟踪文件；结果综合按证据和影响处理重复发现及严重程度分歧。区分独立上下文的审阅与同一上下文中的多次自检，不因方法名称而声称已独立验证。
