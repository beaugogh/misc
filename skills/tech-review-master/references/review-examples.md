# 审阅与修订示例

以下是简化示例，不是外部研究结果。使用时只借鉴判断方式；替换文本中的事实必须来自待审文档或已核实来源。

## 1. 分数需要说明它证明了什么

原文：

> 修改系统可以带来明显收益。成功率从 42% 提高到 59%，另一组从 40% 提高到 62%。

审阅判断：读者不知道修改了什么，两组结果是否可比，或哪项结论值得关注。摘要中逐个罗列分数，不能代替解释。

若来源已说明两组均固定模型、只改工具接口，并在各自留出任务上评估，可建议：

> 在两组固定模型的实验中，简化工具接口后，留出任务的成功率均提高。具体的接口改动和分任务结果见实验表。

这段改写说明了修改对象、共同条件和结果。若执行记录还显示某类工具误调用减少，可以补充该机制；只有成功率时，不要自行补出错误类型或因果链。

## 2. 摘要呈现明确成果

原文：

> 新版本在三组独立测试上超过旧版本，但它能否持续加速自身改进尚无定论。后续还需关注成本、稳定性和兼容性。

若独立测试结论已有依据，摘要可保留：

> 新版本在三组独立测试上均超过旧版本，表明本次修改的收益覆盖了这三组任务。

在方法或讨论部分保留与长期改进有关的未决问题。不要把「超过旧版本」写成「能够持续加速」，也不要推断它适用于所有任务。如果没有任何结论得到充分支持，评审应指出证据不足，而不是生成乐观摘要。

## 3. 展开抽象比较

难以理解：

> 持久修改提高了后续搜索收益。

先核实这句话实际指什么：保存的是经验、代码还是参数？下一轮谁使用这些内容？「收益」指最终分数、搜索费用还是达到目标所用次数？

若原实验确实比较了固定预算下的新旧修改程序，可建议：

> 研究者让新旧两个程序各提出 50 次修改，再比较它们选出的最佳版本。新程序找到的版本任务得分更高。

只有原始资料提供「50 次」时才使用这个数值。句子更具体依赖事实清楚，不依赖增加术语。

## 4. 命名变更只作用于分类

若用户指定分类缩写为 `ctx`、`hrns`、`impr`，同步定义、正文、组合标签和表格。它们只属于该项目的命名约定，不是本技能对其他文档的默认分类。

保护以下内容：

- `C:\work\report.md` 中的盘符。
- 论文「附录 C.2」的编号。
- URL、代码标识符和官方标题。
- 直接引用中的原始用词；如需解释，放在引用之外。

全局替换单个字母会破坏上述内容。审阅时应提出语义范围明确的修改方案，批准后再实施。

## 5. 删除主题时同步整体范围

若用户批准移除某研究方向，检查摘要、概念定义、时间线、方法介绍、分类表、证据表、机构比较和结论。

对同时涉及保留与删除主题的工作，判断相关证据能否单独成立。例如，论文同时改工具和训练模型时，整体得分增益不能自动当作工具改动的效果。可以保留工具修改的机制说明或独立对照，删除与当前范围无关的训练结果。

保留、缩写或移除混合主题案例应在建议中说明，让用户批准具体范围。源论文归档与当前报告范围是不同对象，不因移除报告章节而顺手删除原始资料。

## 6. 批准对应具体建议

| 情况 | 处理方式 |
|---|---|
| 用户只说「审阅这篇报告」 | 读取、核查、提出建议；不改原文 |
| 给出明确替换段落后，用户回复「ok」 | 应用该段及必要的关联同步；不重复确认 |
| 用户说「只改第 2 项」 | 只应用第 2 项及其必要依赖 |
| 用户问「这句话是什么意思」 | 解释含义，必要时提出更清楚的写法；不自动重写整篇 |
| 用户给出新的表达偏好 | 将其用于后续建议；此前批准范围内可继续执行，未获批准的修改仍需提交 |
| 用户明确要求「按这些具体规则直接修改全文」 | 按已给授权完成，不增加一次形式化批准 |
| 已批准文本在应用前被用户改过 | 根据新内容重新判断；实质冲突需要澄清 |

该流程应让批准成为对具体修订的确认，避免反复询问同一授权。

## 7. 先修复章节顺序

输入场景：一篇给首次接入者阅读的指南，目录依次为「部署命令 → 系统历史 → 环境要求 → 验证部署」。环境要求说明部署前必须配置凭据；正文两处重复解释系统历史。

有效建议：将「环境要求」移到「部署命令」之前，保留随后的验证步骤；将重复历史合并，移到背景部分，或在不影响接入目的时建议删除。展示具体移动和删除位置，再请求批准。

验收：能指出会导致操作失败的顺序问题；不能仅把标题润色一遍，或为了凑齐模板新增无依据章节。此判断同样适用于英文的 Requirements、Deploy、Verify 三节。

## 8. 英文摘要保留明确发现

原文：

> In today's rapidly evolving landscape, our solution delivers a transformative leap. In an independent test of 120 requests, version B completed 96 and version A completed 84 under the same timeout. Whether B improves long-term reliability remains inconclusive.

摘要建议：

> In an independent test of 120 requests, version B completed 96, compared with 84 for version A under the same timeout.

验收：删除宣传式开头，将长期可靠性问题移到讨论部分；保留样本数、比较双方和相同超时条件。不能写成普遍可靠性提升，也不能把完成数量误称为成功率增长了 12%。只有指标定义支持时才换算百分比。

## 9. 条件、范围与机器文本

输入场景：操作说明写着「以管理员身份运行 `worker --limit 10`。低于 10 的配置值会被拒绝。随后检查状态。」接口规格没有提供；用户只要求审阅。

有效建议：保留命令及「低于 10」的明确边界；指出「状态」缺少查询方式与预期结果，要求补充。如果其他段落写「10 以下会被拒绝」，标记两处边界可能冲突，核查规格后才统一。

验收：不修改命令，不猜测状态接口，不擅自把 `< 10` 改成 `<= 10`，不修改原文件。英文的 below、at most、up to 也需要按各自含义核对。

## 10. 缺少依据与无需修改

输入 A：只有 “The platform enables a powerful optimization loop.”，没有说明优化对象、处理过程或实验结果。

有效审阅：指出缺少什么信息，并询问优化的是哪一部分、如何运行、有什么证据。可以建议删除空泛评价；不能直接补写缓存、队列或性能数字。

输入 B：「接口返回任务 ID。」或 “The API returns a job ID.”，上下文已清楚定义任务。

有效审阅：保留原句，不制造措辞问题，不要求重写，也不为没有修改内容的审阅请求应用批准。

这些案例供维护时核对判断行为，不要求每次普通文档审阅都执行一轮测试。
