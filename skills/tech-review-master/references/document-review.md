# Technical document review and revision

Read when reviewing the meaning, evidence, structure, or wording of Chinese or English technical prose. Shared scope, approval, and reporting rules live in the [skill entry point](../SKILL.md). Apply the dimensions requested: wording-only work does not become a full requirements or implementation audit. Consult supporting code or contracts when necessary to preserve meaning; load another guide only when its checks are needed for the requested review or a concrete finding.

## 中文与英文

- 对中文和英文采用同等审阅深度，保留文档的原有语言；除非用户要求，不把英文翻成中文，也不把中文改成英语句法。
- 替换文本使用所在段落的语言。评审说明使用用户偏好的语言；混合文档按各段用途处理，保留官方名称、必要术语、引用和代码。
- 中文重点检查名词和抽象词堆叠、缺少主语、层层套接的修饰语、官样表达和翻译腔。英文重点检查名词化、冗长的名词串、生硬搭配、空泛修饰和迂回句式。
- 自然不等于随意或口语化。采用熟悉而准确的词、顺畅的句子和合适的专业语气，不添加俚语、笑话、故意的语病或个人经历来制造「人味」。

## 审阅重点

### 先检查整篇是否讲得通

- 先确定读者已有知识，以及读完后应能理解、判断或完成什么。检查标题、摘要、章节顺序是否服务于这个目标，再处理句子和格式。已有清楚结构时不强行重排。
- 每节应回答一个与文档目的有关的问题。检查是否缺少必要定义或前提、重复回答同一问题、突然引入未解释的概念，或留下标题承诺却未回答的问题。移动、合并和删除应说明具体位置及理由。
- 按文档用途判断内容是否充分：研究报告要交代主张与证据；设计文档要交代问题、约束、选择依据和影响；技术解释要交代输入、处理过程与结果；操作文档要让读者能执行并验证结果。无需把这些内容套成统一目录。
- 用具体材料检查抽象判断：代码、日志、实验或事故事实究竟显示了什么，能支持多大的结论？这是一种核查方法，不规定正文先列证据再说结论；摘要和建议仍优先让读者看到主要发现。
- 用户提供认可的范文时，借鉴其信息密度、解释方式和语气，不移植事实或强套结构。没有范文时沿用项目惯例，不把收集范文作为开始审阅的前提。

### 事实、证据与逻辑

- 找出影响读者判断的关键结论，检查它们是否得到文中数据、实现或来源支持。优先使用已有原始资料和本地归档；需要外部核查时查阅论文、官方文档或实际代码，并记录所用版本。
- 区分作者的主张、实验观察和自己的推断。未核实的内容不能直接定为错误；给出疑点及需要补充的证据。来源不可访问时说明核查边界，不编造事实或引用。
- 对数值说明指标、单位、方向、基线和条件。区分百分比与百分点、平均值与最好结果、尝试次数与成功次数；跨实验比较需要检查任务、模型、预算和版本是否可比。
- 判断收益来自什么。系统整体分数上涨，不自动证明某个组件有效；平台允许修改某组件，也不证明实验实际修改了它。研究报告还应区分用于开发或版本选择的评测与独立最终测试，以及改进成本与执行成本。
- 保留会改变结论含义的前提、例外、否定范围和确定程度。不能把「可能」「尚未证实」润色成肯定结论，也不能用泛泛的风险提示代替具体问题。
- 区分计划、实现、部署和验证状态；「拟支持」不等于「已支持」，实现了也不等于生产环境已启用。区分能力与许可，例如 can/may 和「能够/获准」；原文不明时提出问题，不靠润色作决定。

### 信息价值与执行摘要

- 执行摘要优先呈现**最重要、已有充分依据、与读者有关的明确发现**。说明做了什么、为什么有用，以及证据支持什么范围。
- 尚无定论的实验、研究问题和方法局限通常放在正文的相关位置。摘要中的结论仍须保留必要的简短条件，例如「在该迁移实验中」；不能为了显得确定而扩大适用范围。
- 没有足够可靠的发现时，在评审中说明缺口并提出补证建议，不制造肯定结论。若文档本身就是风险评估或待决策事项说明，按其用途组织摘要。
- 不用论文名、术语或大量分数代替综合结论。摘要中的每个数字都应帮助理解结论或作出判断；详细指标可放入方法正文或对比表。
- 删除「效果明显」「仍需更多研究」「应综合考虑」等缺少具体信息的句子，或补明对象、机制和已有证据。不要以「本文需要说明……」代替说明本身。
- 一段文字应让读者看懂一个主要结论及其依据，避免同时塞入多个概念、多个研究和多个保留意见。

### 自然表达、清晰度与冗余

常规文档审阅必须检查自然度、清晰度、简洁性和含义保真。需要具体判断方法或示例时，查阅[中英文清晰表达指南](clear-prose-zh-en.md)中相关的通用原则、语言章节或示例，不默认通读两种语言的全部案例。复用上下文中已有且未变的指导；纯事实核查等明确限定范围的任务按用户要求执行。

- 识别可观察的问题：套话开场、宣传词、无信息的强调、抽象名词堆叠、重复解释、机械过渡、无必要的对立句、空泛结尾和不自然搭配。「AI 味」是这些表达问题的简称，不据此断言文本作者或生成方式。
- 不只换掉几个「AI 常用词」。找出作者真正要说明的事实、动作或判断；重写句子主干，调整段落顺序，删除没有独立信息的句子。无法确认原意时指出缺口，不替作者编造具体机制。
- 每句话都应提供事实、必要解释、条件、证据或行动。能删除而不损失含义的开场白、强调语、总结和修饰语，优先删掉；同一意思保留最清楚的一处。
- 简洁以读者理解为准。保留理解所需的定义、例子、逻辑连接和必要限定；不要用缩写、密集名词或电报式短句把字数减少、把理解成本提高。
- 朗读式复查：这句话是否像熟悉该技术的人会自然说出的解释？读者是否需要倒回去找主语、猜测代词或重新拆句？有这些问题就继续修订。
- 理解检查：只看修订后的段落及其必要上下文，能否回答这一段要解决的问题？涉及机制时，执行者、动作、条件和结果是否清楚？如果还要另写一段解释这段话，继续修订；缺少事实时指出缺口，不用流畅表达掩盖它。
- 提出问题时说明哪里空泛、重复或难懂，并给出自然的替换文本；仅批注「AI 味太重」或「建议润色」不算有效建议。评审回复本身也应简洁直接。

### 技术表达与术语

- 用具体的执行者、动作、对象和结果解释机制。若必须依靠额外长篇解释才能理解某句，就重写该句。
- 技术术语应帮助表达精确含义。首次出现时解释必要术语；遇到「后续搜索收益」「持久修改」等压缩表达，展开说明实际保存了什么、谁在使用、比较了什么。
- 说明比较时写清比较双方和共同条件，例如「给新旧两个版本相同预算，让它们分别提出修改，再比较修改后的任务成绩」。不要用另一个抽象概念解释原有抽象概念。
- 保持同一概念的称呼一致，尊重用户指定的缩写。重命名只作用于相应概念，不波及 URL、盘符、附录编号、官方标题或代码。
- 中文正文默认使用简洁、克制的语句，保持中英文和数字间的必要空格；一段一行，使用编辑器软换行。标点、引号和称呼服从目标项目习惯，不为统一风格重写固定引用。
- 操作手册额外检查前置条件、执行顺序、预期结果和失败处理；API 文档检查类型、单位、默认值、约束及必填项。缺失信息应提出补充要求，不自行编造。
- 操作步骤先给影响执行的条件或警告，再给动作；必要时将可独立验证的动作拆开。数值范围应明确是否含端点；原文不足以判断时核查定义。句长和词汇检查只能提供线索，不设通用于所有文档的字数上限。

处理摘要取舍、抽象表达、分类重命名或范围收敛时，参阅[审阅与修订示例](review-examples.md)。示例说明判断方法，不规定所有文档使用同一术语或结构。

### 按需读取专项指导

- API 说明、异步状态、参数约束与错误提示：读取 [API 与错误信息](api-and-errors.md)，对中文和英文使用同样的语义检查。
- 部署、操作步骤与故障排查：读取[操作与故障排查](procedures-and-troubleshooting.md)，检查人工动作、系统行为、验证及失败处理。
- 中文术语、单位、排版及 Markdown 换行：读取[术语与排版](terminology-and-typography.md)。项目约定优先；其中的语言偏好不强加给英文文档。
- 用户要求建立项目专属约定时，可参考[项目覆盖模板](project-overrides-example.md)；不为普通审阅自动创建配置。
- 需要检查大批中文 Markdown 时，参阅[可选工具](optional-tools.md)。检查结果不能代替内容审阅；写回工具只在已批准范围内使用。
